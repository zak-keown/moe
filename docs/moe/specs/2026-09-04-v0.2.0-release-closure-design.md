# Moe v0.2.0 Release Closure

**Status:** Approved design. Implementation has not started.

## Purpose

Publish a coordinated Moe `v0.2.0` release from one verified set of six public
plugin artifacts. The release replaces release workflows that currently call
mutation commands which intentionally fail. It also replaces the unsupported
Memory `0.1.5` recovery baseline with the actual published `0.1.4` baseline.

## Release contract

The platform tag is `v0.2.0`. Each public package and its Mint version
authority publishes `0.2.0`:

- `@bubstack/moe-core`
- `@bubstack/moe-backstory`
- `@bubstack/moe-memory`
- `@bubstack/moe-glass`
- `@bubstack/moe-crew`
- `@bubstack/moe-statusline`

The generated plugin trees remain the release payload. Mint builds, packs, and
checks each artifact before publication. Candidate publication sends those exact
tarballs to npm's `next` tag and attaches the same bytes, catalogs, locks, and
checksums to the candidate GitHub release. Stable promotion does not rebuild or
repack. It verifies the candidate records and promotes those exact npm versions
to `latest`.

## Authority and mutation boundary

Only protected GitHub Actions environments may execute publication, release
asset mutation, or npm tag promotion. Developers retain read-only planning and
verification commands; a local `--execute` invocation must refuse mutation.

The candidate and stable workflows require distinct approvals. Candidate work
may create draft/prerelease assets and publish `next`. Stable work may run only
after candidate qualification has produced artifact-hash-bound evidence. It
finalizes the GitHub release and moves the already-published versions to
`latest`.

## Qualification boundary

Stable promotion requires all of the following:

- successful source, artifact, reproducibility, attribution, and package gates;
- real Claude Code and Codex install, update, trust, MCP, and uninstall flows
  on supported macOS and Linux targets;
- Copilot custom-path coverage;
- Memory database migration and rollback qualification from the public
  `@bubstack/moe-memory@0.1.4` release on supported macOS and Linux targets;
- recovery capsules, evidence reports, and platform catalog entries whose
  hashes match the candidate artifacts.

Other harnesses may remain preview only when their catalog records say so.
Node 24 is the qualification floor. The release does not retain Node 22 lanes.

## Required migration

Replace every release-contract occurrence of the planned `0.1.5` predecessor
with `0.1.4`: recovery capsule schemas and assets, rollback implementation and
tests, public API fixtures, migration guidance, release-evidence fixtures, and
workflow inputs. Historical documents may retain `0.1.5` only when clearly
describing the superseded plan.

Update all public package and Mint version authorities to `0.2.0`, regenerate
the plugin artifacts through `pnpm mint`, and update registry, marketplace, and
catalog expectations together. Tests may use arbitrary version strings where
they are merely data; they must use `0.2.0` or `0.1.4` when asserting the
release contract.

## Non-goals

- No local publishing escape hatch.
- No rebuilt artifact during promotion.
- No certification claim for preview-only harnesses.
- No native Windows Memory runtime qualification.
- No release claim based only on structural or unit tests.

## Completion criteria

`v0.2.0-rc.1` records six exact candidate artifacts and complete qualification
evidence. After protected stable approval, `v0.2.0` records the same artifacts,
the six packages resolve to `0.2.0` under `latest`, and the repository's
catalogs, documentation, manifests, and plan state name the completed release.
