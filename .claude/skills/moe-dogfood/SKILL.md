# Dogfooding Moe from this repo

## Run this

```bash
pnpm mint && pnpm build          # only if plugins/ or a package changed
python3 .claude/skills/moe-dogfood/scripts/stage.py
```

It backs up the install, replaces one plugin directory at a time, re-applies the
per-machine repoints, and refuses to finish if any hook or MCP command points at
a file that is not there. Then follow the commands it prints and **restart the
session** — a running one holds the hook registry it loaded at startup.

`--dry-run` reports without writing. `--no-backup` skips the copy.

## The shape of the install

Moe is sideloaded, not installed from a registry. None of the `@tc/*` packages
have ever been published (ProGet needs `PROGET_NPM_AUTH` in CI, which has never
run), so `moe upgrade` cannot work — it targets the git marketplace and npm.

```
repo plugins/            →  ~/.moe/local-marketplace/plugins/   →  Claude Code
(generated by pnpm mint)    (a DIRECTORY marketplace)              (live)
```

Two properties of a directory marketplace drive everything below:

**It loads live.** Claude reads plugins from `~/.moe/local-marketplace`, not from
`~/.claude/plugins/cache/moe/`. A bad stage breaks the running session
immediately. The cache is a copy whose timestamps will look untouched and tell
you nothing happened — that is the single most misleading signal here, so check
the marketplace directory, never the cache, when something looks wrong.

**Sources must be local.** The repo's `.claude-plugin/marketplace.json` lists
`moe-memory` and `moe-glass` with npm sources pointing at that unpublished
scope. The staged copy rewrites every source to `./plugins/<name>`. The script
does this; if you edit the file by hand, do it there and never in the repo.

## Why hand-copying breaks things

Two plugins carry a runtime the repo does not, so the staged copy needs a fix
that cannot be committed:

| Plugin | Needs | Because |
|---|---|---|
| `moe-crew` | `packages/crew/dist` copied to `moe-crew/dist` | its hooks call `${CLAUDE_PLUGIN_ROOT}/dist/emit-event.cjs`, and `plugins/` carries no build output |
| `moe-memory` | **four** files repointed at the globally installed `@tc/moe-memory`: `hooks/hooks.json`, `hooks/moe-mint/hooks.json`, `mcp.json`, `.mcp.json` | its 644MB of dependencies are not worth staging a second copy of |

`rm -rf` on the whole `plugins/` directory followed by a fresh copy destroys
both. That is not a hypothetical: it happened on 2026-09-02 and took down every
hook in the session.

The blast radius is worth understanding, because it is wildly out of proportion
to the mistake. `moe-crew/hooks/hooks.json` registers on **PreToolUse,
UserPromptSubmit, SessionStart, Stop and SessionEnd** — five events, all running
the same missing file. Claude Code reports it as a bare Node module resolution
error with no plugin name attached:

```
PreToolUse:Bash hook error
Failed with non-blocking status code: node:internal/modules/cjs/loader:1520
```

So the symptom is "every hook is broken" and the message names neither the
plugin nor the file. You will look at the plugin you just changed. The culprit
is a plugin you did not touch.

`moe-memory` fails more quietly: its SessionStart sync stops and its MCP server
never starts, so conversation search returns nothing and nothing announces why.

Its four files are the trap worth internalising, because each one looks like the
only one. `mcp.json` and `.mcp.json` sit side by side — the neutral plugin spec
and the Claude Code one, separate files with separate contents.

The fourth is the subtle one. Mint emits a merged `hooks/moe-mint/hooks.json`
alongside the plugin's own `hooks/hooks.json`, and Claude Code **reads and
registers both** — supplement, not replace. It survives that by deduping
exact-duplicate `{matcher, command}` entries at execution time, which works only
while the merged copy stays byte-identical to the source. The reasoning and the
empirical confirmation are in `packages/mint/src/adapters/claude-code.ts` and
`packages/mint/docs/history/2026-08-11-hook-double-fire-findings.md`.

That invariant is what a staging edit breaks. Repoint `hooks/hooks.json` and not
the merged copy and the two entries stop matching, so dedup no longer fires and
Claude registers *both* — the working one and the stale one. The symptom is a
SessionStart error that survives a fix you can see is correct in the file you
edited. `generate()` guarantees the two stay in sync; nothing guarantees it
after generation, which is exactly what staging is.

The lesson generalises past this one plugin: **glob the tree, never a fixed
filename.** Every miss here came from matching one path and assuming it was the
set. The script now walks `hooks/**/hooks.json` and both MCP configs for exactly
this reason.

## Retiring a plugin

When a plugin leaves `.claude-plugin/marketplace.json`, order matters:

1. `claude plugin uninstall <name>@moe` — **before** its directory is removed.
   Uninstalling after leaves the running session firing hooks at a path that no
   longer exists, and it reports `Plugin directory does not exist` on every
   event until you restart.
2. Re-stage (the script drops retired directories and tells you which).
3. `claude plugin marketplace update moe`.
4. Restart the session.

Two traps on the repo side. `pnpm mint` wipes and rewrites the directories it
owns but does not delete one that left the registry, so `plugins/<retired>/`
lingers. And after `git rm -r` takes its files, the empty directory skeleton
stays behind where git cannot see it — `git status` is clean, `pnpm mint:check`
passes, and the stale directory still gets copied into your install. Check with
`ls plugins/`, not with git.

## Diagnosing a broken install

| Symptom | Cause | Fix |
|---|---|---|
| Every hook fails, `cjs/loader` MODULE_NOT_FOUND | `moe-crew/dist` missing from the staged copy | re-stage |
| `Plugin directory does not exist: .../<name>` | plugin uninstalled or removed while a session held it | restart; if it persists, check `enabledPlugins` in `~/.claude/settings.json` |
| Memory search returns nothing, no error | `moe-memory` MCP not repointed (check **both** `mcp.json` and `.mcp.json`) | re-stage |
| Skill edits do not take effect | `pnpm mint` not run, or staged but session not restarted | `pnpm mint`, re-stage, restart |
| Retired plugin still loads | still in `enabledPlugins` | `claude plugin uninstall <name>@moe` |

`~/.claude/settings.json` `enabledPlugins` is the persisted truth about what is
installed. When it disagrees with what the session is doing, the session is
stale and a restart settles it.

## Verifying by hand

The script's check is the same one you would run yourself: expand
`${CLAUDE_PLUGIN_ROOT}` in every hook command and confirm the target exists.
`${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}` nests, so a single-pass brace
substitution silently leaves a stray `}` in the path — collapse innermost-first.

To confirm a hook actually runs, feed it a realistic payload rather than `{}`;
most hooks exit early on an empty one and look fine when they are not:

```bash
R=~/.moe/local-marketplace/plugins/moe-crew
echo '{"session_id":"x","cwd":"'$PWD'","hook_event_name":"PreToolUse",
       "tool_name":"Bash","tool_input":{"command":"ls"}}' \
  | CLAUDE_PLUGIN_ROOT="$R" node "$R/dist/emit-event.cjs"; echo "exit=$?"
```

Exit 0 with no output is success for the event hooks. A SessionStart hook that
has something to say prints one line of JSON with `hookSpecificOutput`.

## Adding a plugin that needs a repoint

If you add a plugin shipping a compiled runtime or an MCP server, add it to
`REPOINTS` in `scripts/stage.py` — `copy_dist` for a build output that can be
staged, `global_cli` for a package too large to duplicate. A stale entry fails
loudly on a missing source path rather than silently producing a broken
install, which is the tradeoff that table is built around.
